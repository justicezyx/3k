## 1. Code is buggy or wrong compared to the design

- **P1 — High.** Two callers of `GET /cpod/job` can both return one unassigned job: the claim updates by primary key, discards `sql.Result`, and then appends the job.
  - Evidence: revised design note §9.2 line 304: “Claim CAS: `UPDATE … SET cpod_id=? WHERE id=? AND (cpod_id='' OR cpod_id IS NULL)` and `RowsAffected==1`. Loser skips emit.” §9.9: “Two islands poll the same job | Blind SET; double emit possible | CAS; one winner.” Code: `internal/scheduler/handler/routes.go` 42–44 registers `GET /cpod/job`; `internal/scheduler/handler/cpod_job_handler.go` 21–22 calls `CpodJob` with no lock. `CpodJob` (`internal/scheduler/logic/cpod_job_logic.go` 38–50) does not call `DB.Transact`. Train update is `WHERE job_id` and the result is discarded (106–112), then the job is appended (122–128). Inference is `WHERE id` (185–190) then append (197). Jupyter is `WHERE id` (260–265). App is `WHERE id` (315–320) then append (326). `UpdateColsByCond` is `ExecCtx` and does not read `RowsAffected` (`internal/scheduler/model/sys_user_job_model.go` 234–240). The node debit is a later `UPDATE` by node `id` (333–341), still outside a transaction. `SELECT … FOR UPDATE` in `internal/scheduler/logic/resource_task_get_logic.go` 48–54 is the admin resource-sync handler (`routes.go` 290), not `/cpod/job`.
- **P2 — High.** Heartbeat writes `gpu_allocatable` from GPUs requested by pods whose `NodeName` is already set.
  - Evidence: §9.2 line 307: “Heartbeat fencing: write observed free to a separate column; `allocatable = max(0, observed − reserved)`. Never clobber reservations.” Code: the only Go writers of `gpu_allocatable` are the assign debit (`cpod_job_logic.go` 333–341) and the status update (`internal/scheduler/logic/cpod_status_logic.go` 87–101). `POST /cpod/status` is `routes.go` 47–48. `CPodObserver.getResourceInfo` counts a container only when `pod.Spec.NodeName` equals the node name (`cpodoperator/internal/synchronizer/cpodobserver.go` 281–297), then sets `GPUAllocatable = GPUTotal - GPUUsed`. No reservation column is read on that path. `NodeInfo.Status` is the node label `status` (247), and `CpodJob`’s candidate query does not read it (58–63).
- **P7 — High.** A non-finetune job with `GpuNumber >= 8` sets replica count to `GpuNumber/8` and leaves `GPURequiredPerReplica` at 0; PyTorch and MPI then request that 0.
  - Evidence: §4.1 line 131: “Multi-node training: `workerReplicas` → PyTorchJob/MPIJob + NCCL IB env + optional RDMA device.” §6.3 line 219: “portal `GpuNumber ≥ 8` sets `workerReplicas = GpuNumber/8` and can leave `GPURequiredPerReplica = 0`.” Code: `SyncJob.Start` calls `processTrainningJobs` (`cpodoperator/internal/synchronizer/syncjob.go` 98–110). That function skips `JobType == "Finetune"` (437–439). `gpuPerWorker` stays 0 when `GpuNumber >= 8` (462–468) and is stored as `GPURequiredPerReplica` (498) with `WorkerReplicas` (513). The reconciler builds `nvidia.com/gpu` from `GPURequiredPerReplica` (`cpodoperator/internal/controller/cpodjob_controller.go` 380–386) and attaches that list on MPI (473) and PyTorch (521). The `> 0` branch only adds a product selector on the general Job (426–430). The `> 1` branch only adds shm on PyTorch (562). Neither writes a non-zero GPU count. PyTorch sets `NprocPerNode` to `WorkerReplicas` when that count is greater than 1 (535–541). FineTune is the other path: `finetune_controller.go` 159 sets `GPURequiredPerReplica: gpuCount`.
- **P8 — High.** A create that stores `cpod_id` is returned on the next pull with no GPU-count check.
  - Evidence: §9.4 line 325: “Filter is hard feasibility (product, count, pin-cluster, not banned, fresh).” §6.2 line 203: “persist row `NeedSend`, optional pin `cpod_id`.” §9.7 line 345: “Unchanged + optional `PinCluster`.” Code: `job_create_logic.go` 90–91 copies `CpodID` and does not query `sys_cpod_node`. `finetune_logic.go` 95–96 does the same. `inference_deploy_logic.go` 109–111 sets `cpod_id` and `StatusAssigned` with no node query, so the pull’s `StatusNotAssigned` loop (171–178) does not run and the default branch appends the row (`cpod_job_logic.go` 201–202). Train rows whose `cpod_id` already equals the caller are appended from `activeJobs` (99–102, 131–140) with no debit and no `GpuAllocatable` test.
- **P10 — Med.** An empty GPU type matches the first fresh node with one free CPU, on any product and any free GPU count.
  - Evidence: §3 M5 line 112: “Placement must honor GPU product.” §9.4 line 325 includes product in the hard filter. Code: the train predicate is `(product match && allocatable >= need) || job.GpuType.String == ""` after `CpuAllocatable >= 1` (`cpod_job_logic.go` 88–93). No later branch in `CpodJob` rejects that match. `JobCreate` copies the request and does not reject an empty type (`job_create_logic.go` 75–76). `gpu_type` is nullable (`deployment/sxcloud/database/init.sql` 367). `httpx.Parse` on `JobCreateReq` (`job_create_handler.go` 16) does not add a non-empty check beyond the struct tag `json:"gpuType"`.

## 2. Code is incomplete compared to the design

- **P12 — High.** The checkpoint PVC is created with a controlling owner ref to the CPodJob, and no reconcile strips that ref.
  - Evidence: §9.3 line 313: “CKPT today is a PVC + OwnerRef cascade — delete job deletes checkpoint.” Line 317: “durable copy off-island (OSS) or PVC not cascaded on drain.” Code: `GetCKPTPVC` creates `{name}-ckpt` with `generateOwnerRefCPodJob` (`cpodoperator/internal/controller/cpodjob_controller.go` 717–731). That helper sets `Controller` and `BlockOwnerDeletion` (823–832). `releaseSavedModel` removes an owner ref only on the model-save PVC (952–976) and returns immediately when the model-save path is empty (953–954). FineTune owns its CPodJob the same way (`finetune_controller.go` 148–150, 257–270) and sets `CKPTPath` (165–166), so a FineTune delete follows that owner chain. `SyncJob.Start` (98–114) has no CKPT detach.
- **P26 — Med.** The heartbeat resource payload has no queue depth, RDMA domain, health/drain value, or inventory epoch.
  - Evidence: §9.4 line 323: “Enrich heartbeat: queue depth, RDMA/topology domain, health/drain, inventory epoch.” Code: `ResourceInfo` is `GPUSummaries`, `CPODVersion`, `Nodes`, `CPODID`, `Caches` (`internal/scheduler/types/types.go` 920–926). `NodeInfo` (801–814) has no queue, RDMA domain, or epoch. `CPodObserver.getResourceInfo` sets `Status` from the label `status` (`cpodobserver.go` 247) and does not set those four fields. `CpodJob` does not read that label (58–63).

## 3. The design is missing use cases

- **P11 — High.** User stop and overdraft stop never release the island or a reservation.
  - Rank basis: README audiences include the compute user who trains, finetunes, and infers (`README.md` 36). Those jobs have stop or delete routes: `POST /job/stop` (`routes.go` 62), `POST /api/job/gpu/stop` (372), `POST /api/job/inference/stop` (387), jupyterlab delete (178–193), and `/app/job` delete (310–320).
  - Quote: §9.1 lines 288–295 are “Create job → Admit → Place → Bind → Deliver” and “Reconcile assigned rows → CRs → kube bind → Heartbeat”. User stop does not appear. §9.9’s closest row is “Owner reclaim | Manual | Same until Phase B.” Overdraft stop does not appear.
  - Code: `job_stop_logic.go` 28 calls `DeleteSoftByName`, which sets `deleted=1` and `update_time` only (`sys_user_job_model.go` 113–118). `jobs_del_logic.go` 46–74 sets train `deleted`, inference `StatusStopped` plus `obtain_status` not-need-send, and jupyter `StatusStopped`. None of those writes, and none of the terminal status writes (`cpod_status_logic.go` 147–151), assign `cpod_id` or `sys_cpod_node`. A repo search found no assignment that clears `cpod_id`.
- **P14 — Med.** A job that matches no node stays need-send, and the portal job has no reason field.
  - Rank basis: README names `2h8g` as “2 nodes 16 GPUs” (`README.md` 26), and training create is `POST /api/job/training` (`cmd/scheduler/sdk.api` 150). That shape cannot pass the one-node count in P6, so the no-reason result is on a documented job, not a hypothetical kind.
  - Quote: §4.1 line 128: “Status mirrors to the portal (Running / Succeeded / Failed / uploading).” A filter-miss status is absent from that list. §9.9’s rows are double-poll, heartbeat clobber, portal down, island death, owner reclaim, data missing, and partial multi-node start. §7 line 261 asks for “One structured placement decision log: filters, winner, claim won/lost,” which is a log line, not a job column.
  - Code: `Job` in `cmd/scheduler/scheduler.api` 176–199 has `ObtainStatus` and no reason field. `job_create_logic.go` 128–134 returns `JobId` after insert. The unmatched train row is left at need-send (`cpod_job_logic.go` 70–73, 83–98).
- **P23 — Med.** Island-owner payment has no API and no table in the refined design.
  - Rank basis: README’s second audience is the cluster owner (`README.md` 37, 算力源). Supplier register exists and writes `user_type` plus `company_id` (`register_logic.go` 102–117) and then a consumer-style balance row (138). Routes expose `/user/register/:code` (238) and `/pay/balance` (208). No route name is a provider payout.
  - Quote: §1 line 52: “Join with an existing Kubernetes GPU island; keep local operational control; pull work; get paid.” Self-join is not missing: §2.1 line 71 says “Partial: pull + heartbeat.” §9.7 lines 345–348 list create, `GET /cpod/job`, `POST /cpod/status`, and CRDs. A pay API is absent. §9.8 lines 352–355 add node columns and job claim columns, and no payout table.
  - Code: the first `sys_cpod_node` insert found is the status handler (`cpod_status_logic.go` 62–79). `NodeAdd` proxies `POST {K8S.BaseApi}/add-node` and does not insert a pay row (`node_add_logic.go` 30–67). Billing tables are `user_balance`, `user_billing`, and `user_recharge` (`init.sql` 423–494).

## 4. The design is low quality given the known information

- **P3 — High.** `reserved_gpu` is an optional node counter with no job id, and no sentence names a decrease.
  - Quote: §9.2 line 305: “Debit CAS: `inv_version` (and optional `reserved_gpu`) on `sys_cpod_node`; `WHERE inv_version=? AND gpu_allocatable>=?`.” Line 307: “`allocatable = max(0, observed − reserved)`. Never clobber reservations.” §9.8 lines 352–355: “`sys_cpod_node: + inv_version, reserved_gpu, gpu_observed_free`” and “`inv_lease` (TTL reaper) — v1.1, not required for CAS.” A writer that decreases `reserved_gpu` on success, failure, stop, overdraft, or heartbeat expiry is absent from §9.
- **P13 — High.** Drain does not name who sets the marker, and re-admit does not name the status write, the product check, or a reservation release.
  - Quote: §9.3 line 318: “Drain: island marks draining (who may: owner or ops — still OPEN in scale packet; do not invent).” Line 319: “Central clears sticky `cpod_id` and re-admits.” `obtain_status` and `work_status` do not appear in §9.3. Code values that a status edge would have to name: `internal/scheduler/model/consts.go` 46–47 (`StatusObtainNeedSend = 0`, `StatusObtainNotNeedSend = 1`).
- **P15 — High.** The claim text updates `WHERE id` on one `job`, which is not the train key and not one completion write.
  - Quote: §9.2 line 304 uses `WHERE id=?`. §9.8 line 354: “job: `cpod_id` CAS; optional `scheduled_node`; `obtain_status`.” §10 line 374: “different packing: sticky long jobs vs replica infer on KServe/Ray.” A per-table key or a completion write is absent from §9.8. Code: train primary key is `job_id` and there is no `id` column (`init.sql` 357–387); inference primary key is `id` (126–148). Terminal train sets `obtain_status` (`cpod_status_logic.go` 147–151). Inference success sets `obtain_status` (210–214). Jupyter and app success set `status` and `end_time` only (280–283, 349–352).
- **P4 — High.** Thirty minutes of silence only drops the node from candidates, while the failure row says island death is drain plus re-admit.
  - Quote: §3 M7 line 114: “`updated_at > NOW()-30 MINUTE` is eligibility. It is not fencing.” §9.2 line 307: “Keep 30m as health only (M7).” §9.3 line 318 leaves the drain mark open. §9.9: “Island death, sticky job | Stranded | Drain + re-admit (Phase B).” No sentence ties the 30-minute predicate to that drain mark. Code: candidates are `updated_at > NOW() - INTERVAL 30 MINUTE` (`cpod_job_logic.go` 58–63). A job already on this `cpod_id` is re-emitted with no freshness check (99–102).
- **P19 — High.** The platform line says meter quota and balance, and the control loop has no bill write and no insolvency stop.
  - Quote: §1 line 53: “Match work to spare capacity, meter quota/balance, without operating every DC’s kubelet.” §9.1 lines 288–295 end at heartbeat. Bill, cron, and balance stop are absent from that loop. Code: `cmd/scheduler/scheduler.go` 106–113 registers `BillingManager.Update` every minute at second 0 and `BalanceManager.Update` at second 10. `billing.go` 34–37 returns immediately unless `Billing.CronBilling`. `balance.go` 33–36 returns unless `Billing.CronBalance`, and 130–136 calls `JobsDel` when `balance < 0`. `cmd/scheduler/etc/scheduler-api_prod.yaml` 49–50 sets both flags `Yes`. `scheduler-api.yaml` 47–48 sets both `No`.
- **P9 — Med.** One place step and one hard filter are written next to four matchers, two of which skip capacity.
  - Quote: §6.3 line 217: “App jobs skip capacity. Jupyter with empty GPU product can assign with no node check.” §9.1 line 290: “Place: filter islands/nodes → pick.” §9.4 line 325: “Filter is hard feasibility (product, count, pin-cluster, not banned, fresh).” CPU and memory floors are absent from that list. Code: train CPU ≥ 1 (`cpod_job_logic.go` 86–97); inference CPU ≥ 4 and 50GiB (171–178); empty `GpuProd` sets `assigned = true` (240–241); app sets `cpod_id` with no capacity predicate (314–320).
- **P21 — Med.** Objective P4 names org beside quota, and the admit rule the note keeps is a per-user sum.
  - Quote: §2.1 line 72: “Quota, org, balance — commercial admission before GPUs burn.” §4.1 line 126: “System rejects if balance < 0 or GPU quota (running sum) exceeded — or allows if no quota row.” §9.1 line 289: “Admit (quota/balance) unchanged.” An org key is absent from those three sentences. Code: `internal/scheduler/job/quota.go` 19–22 loads `new_user_id` and `resource`. `sys_quota` has no org column (`init.sql` 262–271).
- **P27 — Med.** The checkpoint target is an off-island copy or a non-cascaded PVC, with no flush signal and no resume read.
  - Quote: §9.3 line 317: “CKPT contract: durable copy off-island (OSS) or PVC not cascaded on drain.” Flush, signal, and which copy the next island mounts are absent from §9.3. Line 319 says only “clears sticky `cpod_id` and re-admits.”
- **P28 — Med.** The control-loop paragraph uses objective id P4 for create-time bind and tells the poll path to score across the fleet.
  - Quote: §9.1 line 298: “If M2 forbids inbound notify, bind still happens on any poll using global scoring, but commit uses CAS; optional P4 is create-time bind.” §2.1 line 72 uses P4 for “Quota, org, balance.” §2.4 line 96: “Cross-island gang / Borg-style global scorer.” §9.6 line 339: “Dual bind paths without a feature flag.” §9.5 lines 329–331 keep today’s bind “on the winning poll” and say “Do not build an event mesh.”
- **P29 — Med.** Inference packing is “replica infer,” and the data-model delta is still one sticky `cpod_id` with no replica field.
  - Quote: §10 line 374: “different packing: sticky long jobs vs replica infer on KServe/Ray.” §9.8 line 354: “job: `cpod_id` CAS; optional `scheduled_node`; `obtain_status`.” Replica count is absent from that delta. Code already stores the bounds elsewhere: `inference_deploy_logic.go` 85–86 writes `MinInstances` and `MaxInstances` into metadata JSON, and `syncjob.go` 725–726 sets KServe `MinReplicas` / `MaxReplicas`. `sys_inference` itself has no replica column (`init.sql` 126–151).
- **P24 — Low.** Cache locality is a soft score with no named input.
  - Quote: §9.4 line 325: “resource headroom, load balance, cache locality, cost.” `sys_cpod_cache` does not appear in §9.4. Code: the status handler inserts and updates that table (`cpod_status_logic.go` 406–424). A search of `internal/scheduler/logic` and `internal/scheduler/job` finds `CpodCacheModel` only in `cpod_status_logic.go`.
- **P30 — Low.** Multi-node RDMA is described with two node labels, and the note does not pick one.
  - Quote: §6.4 line 229: “RDMA if ≥2 nodes labeled `rdma.available`; e2e uses `rdma.capable` (label split).” §9.4 line 323 says “RDMA/topology domain” and does not name either label. Code: `cpodjob_controller.go` 940–943 lists `feature.node.kubernetes.io/rdma.available`. `e2e/a_ib_test.go` 35 lists `feature.node.kubernetes.io/rdma.capable`.
- **P31 — Low.** The hard filter includes “not banned” and names no table, column, or API.
  - Quote: §9.4 line 325: “Filter is hard feasibility (product, count, pin-cluster, not banned, fresh).” A ban store is absent from §9.7 and §9.8. Code: `cpod_job_logic.go` 46–49 rejects the caller when `Config.BannedCpod[req.CpodId]` is set, before the node query.

## 5. The design is wrong

- **P6 — High.** Place still requires one node with `GpuAllocatable >= GpuNumber`, so a 16-GPU job on two 8-GPU nodes never binds.
  - Quote: §6.3 line 219: “central first-fit still requires one node with `GpuAllocatable >= GpuNumber`.” §9.1 line 290: “Place: filter islands/nodes → pick # still first-fit or WNS-class scores.” §9 does not replace the one-node test. §9.4 line 325 lists “count” and does not define it as a sum across nodes. §4.1 line 131 requires multi-node training via `workerReplicas`. §2.3 line 88: “Which-node stays on the island.” Code: `cpod_job_logic.go` 91 compares one row’s `GpuAllocatable` to `GpuNumber`. README `2h8g` is “2 nodes 16 GPUs” (`README.md` 26).
- **P17 — High.** Unchanged admit counts only running train, inference, and jupyter GPUs, allows a missing quota row, and does not count app jobs, so not-yet-running work overshoots the quota.
  - Quote: §9.1 line 289: “Admit (quota/balance) unchanged.” §4.1 line 126: “System rejects if balance < 0 or GPU quota (running sum) exceeded — or allows if no quota row (shipped behavior; call it out).” §2.3 line 86: “fail-closed on insolvency.” §4.2 line 137: “no unbounded over-commit under concurrent island polls.” Code: `quota.go` 23–26 returns ok when the row is missing. The sum is `work_status` / `status` `StatusRunning` for train (32–36), inference (43–51), and jupyter (57–63). The file does not reference an app model. `/app/job` is registered (`routes.go` 310–320).
- **P18 — Med.** Balance admit is a less-than-zero read before the insert, so two creates can both pass on one balance.
  - Quote: §4.1 line 126: “rejects if balance < 0.” §9.1 line 289: “Admit (quota/balance) unchanged.” §2.3 line 86: “fail-closed on insolvency.” §9.2 line 306 wraps “claim+debit” in `DB.Transact`, not the create. Code: `job_create_logic.go` 44–53 reads `user_balance` and rejects only `balance < 0`, then inserts at 128. The same read-then-insert is `finetune_logic.go` 47–53 and `inference_deploy_logic.go` 41–49. A search of those three files finds no `Transact`. `user_balance` primary key is `id` only (`init.sql` 423–430), so the read is not a row lock.

## 6. The design can be enhanced

- **P33 — Med.** Make the heartbeat the only writer of `gpu_allocatable`, and have debit insert a reservation and require `observed_free − reserved >= need`.
  - Quote: §9.2 line 305 guards debit with `gpu_allocatable>=?`. Line 307 also sets `allocatable = max(0, observed − reserved)`. The note does not say which of those two writes wins.
- **P34 — Med.** Store one reservation row per claim (`kind`, workload id, `cpod_id`, `gpu_n`, `expires_at`) and set `reserved_gpu` to the sum of unexpired rows.
  - Quote: §9.8 line 355: “optional: `inv_lease` (TTL reaper) — v1.1, not required for CAS.” §11 line 382: “Alerts: heartbeat stale beyond 30m and reserved > 0 (stranded lease).” The v1 delta does not give that alert a row to expire.
- **P32 — Low.** Add a unique key on `sys_quota (new_user_id, resource)` so the admit lookup has one row.
  - Quote: §4.1 line 126 describes one quota check and does not mention a unique key. Code: `init.sql` 262–271, primary key `id`, secondary key `idx_user_id` only. `quota.go` 19–22 uses `FindOneByQuery` on `new_user_id` and `resource`.

## Removed after verification

- **P5.** `sys_cpod_main` has no writer in the pin, and the design note never names that table.
- **P16.** The failure row “Data missing | CPodJob Failed” matches the NotFound branches that set `JobFailed` (`cpodjob_controller.go` 317–321 and 349–352). The 20s requeue is `PrepareData` (150–153), a different error.
- **P20.** No route, README entry, or request field is a replayed create. `JobCreate` mints a new `train-` name on every call (`job_create_logic.go` 78–83).
- **P22.** Section 1’s three actors match the README’s three audiences (`README.md` 36–38). The note never says those actors are the `user_type` or `admin` columns.
